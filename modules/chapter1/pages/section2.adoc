= How the Automation Orchestrator Works

Let's First talk about Installation and Configuration

The Automation Orchestrator is now available as a separately licensed add-on SKU to Red Hat Ansible Automation Platform, providing full Red Hat support entitlement including access to support cases, security advisories, and lifecycle guarantees.

**To get started**:

Once an add-on SKU has been purchased and enabled, there are three methods to install the automation orchestrator. Installation then happens in two phases: first you install the operator, then you create an instance.

You have three ways to install the automation orchestrator:

* OpenShift CLI  using `oc` commands to create an Operator Lifecycle Manager (OLM) subscription. This is the recommended method for production and CLI-based provisioning workflows.
* OpenShift Web Console  install directly from OperatorHub for a guided, graphical experience.
 
[Note]
Once the operator is running, you create an AutomationOrchestrator custom resource to deploy the application and configure its components  including your PostgreSQL database connection, ingress settings, and optional integrations such as S3 storage and an LLM provider.

* aapctl CLI (Technology Preview)  a companion CLI that installs the operator and configures the deployment in a single step, supporting GitOps workflows through manifest generation.

[First Login]
After deployment, retrieve the initial admin password from the OpenShift secret and log in to the web interface. From there, connect your Ansible Automation Platform instance to enable single sign-on and job dispatch, then configure your LLM provider credential when you are ready to use AI task agent steps in your workflows.

When you log in to the automation orchestrator, you will see six key areas in the sidebar:

|===

|Workflow Builder
|Where you design automation workflows on the canvas

|Workflows
|Lists all saved workflows you have access to

|Workflow Runs
|Shows the execution history of all workflow runs

|Where human approval requests are reviewed and acted on

|System Administration

These six areas cover the full lifecycle of a workflow from design to execution to governance.

== The Canvas Your Workflow Design Surface

The canvas is where everything comes together. Think of it as a visual programming surface where you place steps, connect them in order, and define the logic of your automation.

When you open the Workflow Builder, you start with a blank canvas and a trigger step on the right-hand panel. From there, you add steps, connect them with lines that define execution order, and configure each step using the details panel.

The canvas has four main areas:

- Top toolbar: workflow name and version state (Draft, Published, or Unpublished changes), save, run, publish, and options
- Selection of a project : where all your workflows reside
- Canvas workspace : the central area where you arrange and connect steps
- Details panel: appears when you click a step; shows Input, Parameters, and Output for that step

As you build, the canvas gives you a live picture of your workflow. When you run it, the same canvas becomes your monitoring view on each step lights up with its current state in real time.

=== Understanding Steps

[NOTE ON TERMINOLOGY]
Steps were previously called nodes in earlier versions of the tool. You may still see the term "node" in some places within the product UI, but the current and correct term is steps.

Steps are the building blocks of every workflow. Each step represents a discrete action or decision point. You connect steps together to define the order of execution and the logic of your automation.

There are six categories of steps available in the step palette:

- Triggers: Every workflow starts with exactly one trigger. This defines how and when the workflow begins.
- Task Agent:  Bring AI-assisted reasoning into your workflow using a large language model that can reason, call tools, and return structured output.
- Logic:  Shape the execution path: conditions, switches, loops, waits, and converge points.
- Approval:  Pause the workflow at a defined point and wait for a human decision before continuing.
- AAP Execution:  Run Ansible job templates or workflow templates from your connected Ansible Automation Platform instance.
- Action:  Do the actual work: calling REST APIs, running scripts, and connecting to external systems.


Each step displays the relevant panels: 

- Input : data coming in from upstream steps Schema, table, JSON. 
- Parameters : The Parameters tab contains the configuration fields specific to the step type. Each step type has different parameters. 
- Output : what this step produces for downstream steps

You can also configure the following settings on most step types:

- On failure : controls what happens if the step fails: stop the workflow, continue with errors, or use the system default.
.. System default uses the platform-wide behavior configured by your administrator in System Administration → Settings. The platform default is Stop.
.. Continue on failure: the step fails but downstream steps continue executing. The overall run completes with a Completed with errors status.
.. Stop workflow or branch on failure: execution halts at this step. If the step is on a parallel branch, only that branch stops.

- Timeout : when the duration expires, the step is marked as Failed and On failure behavior is applied. If no timeout is set, the step uses the global default configured in Settings.

- Retry policy : only available for HTTP request and AAP Execution steps:
.. Max retries: number of retry attempts after the first failure (0 disables retries)
.. Initial interval: delay in seconds before the first retry
.. Max interval: caps how long the delay can grow
.. Backoff coefficient: set to 1.0 for fixed-interval retries, greater than 1.0 for exponential backoff


The key point the feedback is driving at: "system default" is meaningless unless the course tells practitioners where that default is set — which is System Administration → Settings. Without that, they have no idea how to change it.
